# Common traps

Part of [[Product Design Prompt Kit]].

| Instead of | Say | Why |
|---|---|---|
| "Make it modern and clean." | "Calm, quiet, low density. One accent colour. Reference: Things 3." | Taste words are vague. Name density, personality and a reference app. |
| Asking for one screen in isolation | "Map the flow first, then design each screen in it." | Screens only make sense inside a flow. |
| Designing the happy path only | "Show empty, loading, error and offline states too." | Real users spend a lot of time in the unhappy paths. |
| Not naming a platform | "iOS, following Apple HIG." | Web, iOS and Android differ in navigation, targets and overlays. |
| Jumping straight to high fidelity | "Low-fidelity wireframes first." | Polish hides structural problems and makes you reluctant to change. |
| "Make it pop." | "The Save button should be read first, the date last." | Say what should draw the eye, in order. |
| Asking for everything in one prompt | "One plane per prompt, feeding each answer forward." | Big prompts produce shallow answers across the board. |
| Accepting the first output | "Critique this against Nielsen's heuristics, then revise." | The first draft is a starting point. Iteration is the job. |
| Asking for a feature | "Users lose ideas because filing takes too long." | Give the problem. A feature request skips better solutions. |
| Lorem ipsum content | "Use real notes, including a very long one." | Fake text hides real lengths and priorities. |
